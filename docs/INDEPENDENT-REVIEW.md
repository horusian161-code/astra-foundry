Проверка исходников и локального исполнения проведена 2026-10-08. Доступ к серверу,
браузеру Foundry и игровым документам не использовался. Проверка не удостоверяет
совместимость с установленной сборкой CPR.

## Подтверждённые дефекты

### R1. Неопределённое исполнение отображается как промах и применение

Файлы: `scripts/demo/workflow-demo.mjs`, `scripts/ui/workflow-render.mjs`.

`engine.execute` штатно возвращает запись со состоянием `uncertain` либо `failed`
без исключения. До исправления обработчик переключал экран на `result` без проверки
состояния; рендер воспринимал отсутствующее `hit` как промах и всегда писал
«Применено один раз».

Воспроизводимый локальный случай: создать ledger сценария с `ammo: 0`, подготовить
запрос через engine, выбрать `accept`, вызвать execute и передать возвращённую
проекцию в экран результата. В обычной работе тот же случай получается, если
магазин опустеет в другом окне между подготовкой и исполнением.

Наблюдение до исправления: `state: uncertain`, `result: null`, `receipt: null`; HTML
одновременно содержал «ПРОМАХ» и «Применено один раз».

Исправление: `workflowPhaseForOperation` и сам renderer переходят на результат
только для `resolved` с квитанцией `applied: true` и объектом result; остальные
исходы направляют в сверку. Независимые R1-тесты проверяют оба пути.

### R2. Сверка принимает квитанцию другого payload/сценария

Файлы: `scripts/demo/attack-operation.mjs`, `scripts/demo/ledger.mjs`.

До исправления демоквитанция искалась только по request ID. `applyOnce` защищал
namespace и command signature, но `reconcile` обходил эти проверки.

Воспроизводимый случай: ledger сохраняет исполненный запрос ID `review-reused-id`
для `namespace: encounter-old`, DV 13. После создания нового operation store
подготовить тот же ID для `namespace: encounter-new`, DV 25, затем исполнить и
вызвать recover. Исполнение правильно даёт `uncertain` из-за несовпадения
квитанции, а recover ошибочно переводит запрос в `resolved` с DV 13. Ресурсы нового
сценария остаются `25 / 40 / 11`.

Исправление: `verifiedReceipt` сверяет namespace и точный command signature;
command содержит идентичность исходных аргументов, магазина `ammoKey` и выбора защиты. Независимый
R2-тест использует два разных выбора с одинаковым числовым DV, чтобы одинаковые
цифры не могли подменить доказательство исполнения. Для журналов и базы аналогичная
проверка signature уже существует в `domainReceipt`.

### R3. Автор pending-операции не обозначался отдельно от selected

Файл: `scripts/demo/workflow-demo.mjs`.

После подготовки атакующий фиксировался в `record.preview.attackerId`. При
выборе другого персонажа ожидание сохранялось, но явной подписи автора атаки не
было. Это дефект идентичности представления, а не изменение сохранённых аргументов.
Исправление: имена автора, цели и оружия сохраняются при подготовке; панель
ожидания и результат показывают их из операции. Независимый R3-тест проходит
полный путь prepare → public projection → renderer, включая изменение исходного
args после подготовки и смену выбранного персонажа.

## Изменения после первой проверки

По исходникам подтверждено: `ammoByKey` хранит независимые магазины шести
демопрофилей; `ammoKey` соответствует паре attacker ID / weapon ID и входит в
подписываемую идентичность запроса. Старое поле `ammo` остаётся совместимым
представлением только магазина `proxy:rifle`. Ограниченное старое состояние
`ammo / targetHP / targetSP` мигрирует в schemaVersion 2; неизвестная либо
повреждённая схема отклоняется без автоматического обнуления.

Запрос использует магазин, сохранённый при подготовке. Выбор другого персонажа
или оружия не перенаправляет расход сохранённой операции. Это подтверждено
чтением descriptor/ledger и сохранёнными тестами автора; отдельная независимая
проверка IndexedDB здесь не выполнялась. Домен целей всё ещё содержит одну
демоцель, а не универсальный реестр ресурсов всех участников CPR.

Ручной DV теперь отделяет черновой ввод от `manualOverride`: предпросмотр
применяет только подтверждённое значение. Выдачу настоящих прав GM это не
реализует; переключатель относится к локальному стенду.

## Границы результата

Роли демостенда намеренно переключаются одним клиентом. Такое локальное
переключение не проверяет аутентификацию, выдачу прав или сокеты. Private state
IndexedDB доступен владельцу браузера; для реального запроса защиты private
запись должна находиться только у полномочного исполнителя.

Независимая проверка не заменяет стенд с двумя настоящими клиентами Foundry,
проверку установленной системы, восстановление после сетевого разрыва и
подтверждение системного API игровых операций.

CAS двух вкладок одного origin и сохранение IndexedDB не проверяют транспорт
между браузерами, серверную аутентификацию, выбор ответственного исполнителя
или работу при закрытых клиентах. Проверка fence перед отдельной доменной
транзакцией также не является универсальной гарантией exactly-once для Foundry.
Игровой адаптер и его атомарная обработка квитанций остаются обязательной
границей будущей интеграции.
