# Astra SDK: проверенная переиспользуемость в alpha 0.2

Здесь описаны **реальные локальные адаптеры**, а не список будущих возможностей.
Оба работают через `OperationEngine` из `scripts/sdk/index.mjs`. Они не импортируют CPR,
Foundry `Actor`, `Combat`, боевой HUD или расчёт оружия. Данные демонстрационные.

## Что реализовано

| Общий код | Интерактивный журнал | Управление базой или кораблём |
|---|---|---|
| `OperationEngine` | Подготовка и выполнение выбора ветки | Подготовка и выполнение резервирования, списания и освобождения |
| Реестр и `engine.catalog()` | `journal.choose`, схема аргументов, проверка, права, preview, execute, reconcile | `base.reserve`, `base.commit`, `base.release`, те же точки расширения |
| `MemoryStore` из SDK | Записи запросов, состояние операции, версия, lease и fence | Те же записи и защита от повторного request ID |
| `MemoryDomainRepository` из examples | Одновременная фиксация открытого этапа и квитанции | Одновременная фиксация ресурсов, часов проекта и квитанции |
| `publicView` SDK и проекции адаптеров | В ответ игроку попадают только уже раскрытые этапы | Доступ к точным ресурсам только у редактора базы или GM |
| `OperationError` | `rights`, `missing-data`, `conflict`, `invalid-input` | Те же коды, без подстановки нуля вместо неизвестного ресурса |
| Сверка по квитанции адаптера | Доказательство того, что этап уже открыт | Доказательство того, что списание уже было выполнено |

`scripts/examples/index.mjs` создаёт **один экземпляр** `OperationEngine` с четырьмя
операциями двух модулей. Отдельные фабрики `createJournalDemo()` и `createBaseDemo()`
доступны для изолированных демонстраций. Общие классы не содержат правил этих модулей:
переходы журнала и ресурсы базы находятся в собственных адаптерах.

## Журнал: выбор ветки

Исходное досье содержит раскрытый этап «Входящий сигнал» и два закрытых продолжения.
Игрок выбирает «Проверить связь» или «Открыть архив».

1. `prepare()` проверяет редактора и аргументы. Preview содержит текст доступного
   выбора. Он не открывает продолжение и не передаёт текст закрытого этапа.
2. `execute()` ещё раз проверяет доступ и актуальность ветки. Выбранное продолжение
   открывается в локальном состоянии вместе с записью request ID.
3. Повтор того же request ID возвращает прежний результат. Новый request ID для той же
   уже выбранной ветки даёт `alreadyOpen: true` и пустой список изменений.
4. Выбор другой ветки после первого выбора возвращает `conflict`. Пользователь без
   доступа получает `rights`; `journalView()` не включает содержимое этапов в его ответ.

Это необратимый выбор в данном демонстрационном сценарии. Универсального отката
раскрытой информации нет. Редактор настоящего журнала, импорт его страниц и запись
Foundry `JournalEntryPage` ещё не реализованы.

## База: резервирование → выполнение → квитанция

В демонстрации у базы «Маяк» есть 5 запчастей и проект «Восстановить антенну» с часами
прогресса 0/4. Сценарий резервирует 2 запчасти для продвижения на 2 деления.

| Операция | Проверка | Изменение |
|---|---|---|
| `base.reserve` | Редактор, известный остаток, свободные запчасти и деления проекта, свободный ID резерва | Создаёт резерв. Остаток остаётся 5, часы остаются 0/4 |
| `base.commit` | Владелец резерва или GM; повторная проверка актуальных ресурсов и часов | Остаток становится 3, часы — 2/4; оба изменения и квитанция фиксируются одним локальным CAS |
| `base.release` | Владелец резерва или GM; резерв ещё не списан | Освобождает резерв. Остаток и часы не меняются |

Повторный `base.commit` с тем же request ID возвращает прежнюю квитанцию. Запрос с
новым request ID к уже выполненному резерву возвращает `spent: 0`, `alreadyCommitted: true`
и `originalSpent: 2`. Ресурс остаётся 3. Повторное нажатие не создаёт второе списание.

Два одновременно подготовленных резерва проверяются ещё раз при фиксации.
Синхронный CAS локального доменного хранилища позволяет выполнить один из конфликтующих
резервов и отклонить другой, не допуская отрицательного остатка. Значение `null` для
ресурса или часов возвращает `missing-data`; неизвестное значение не трактуется как ноль.
Изменение остатка после подготовки приводит к `conflict` и сохраняет резерв для ручного
решения. `base.release` не отменяет уже выполненную работу.

Это общая модель ресурсов и проектов, пригодная для базы, корабля или производства.
Стоимость и продвижение здесь задаются демонстрационным сценарием. Правила конкретной
игры должны проверяться отдельным адаптером.

## Запуск через общий API

```js
import {createReusableDemo, journalView, baseView} from './scripts/examples/index.mjs';

const {engine, repository} = createReusableDemo();
const principal = {id: 'player-1', role: 'player'};

await engine.prepare({
  operation: 'journal.choose', requestId: 'journal-radio-1', principal,
  args: {journalId: 'dossier', stageId: 'arrival', choiceId: 'radio'}
});
await engine.execute('journal-radio-1', {principal});
console.log(journalView(repository, 'dossier', principal));

await engine.prepare({
  operation: 'base.reserve', requestId: 'reserve-antenna-1', principal,
  args: {baseId: 'workshop', reservationId: 'repair-1', resourceId: 'parts',
    quantity: 2, projectId: 'antenna', steps: 2}
});
await engine.execute('reserve-antenna-1', {principal});

await engine.prepare({
  operation: 'base.commit', requestId: 'commit-antenna-1', principal,
  args: {baseId: 'workshop', reservationId: 'repair-1'}
});
console.log(await engine.execute('commit-antenna-1', {principal}));
console.log(baseView(repository, 'workshop', principal)); // 3 запчасти, 2/4
```

## Сбой между фиксацией домена и записью результата процесса

Доменное состояние и его квитанция фиксируются вместе. Запись результата
`OperationEngine` находится в другом хранилище. Между ними существует реальный зазор;
мы не называем такую архитектуру распределённым exactly-once исполнением.

Если обработчик фиксирует ресурс, а затем завершение процесса теряется, SDK оставляет
операцию `uncertain`. `reconcile()` читает доменную квитанцию, проверяет её сигнатуру и
возвращает доказанный результат. `engine.recover()` может завершить запись процесса
без второго списания. Отдельный тест воспроизводит этот зазор.

`assertFence()` проверяется перед локальным CAS. Это защищает данный стенд от устаревшего
исполнителя, но проверка fence в одном хранилище не является атомарной блокировкой
Foundry-документа в другом хранилище. Настоящему системному адаптеру нужен собственный
доказуемый механизм согласования и квитанций.

## Что тестируется и где граница

`node --test tests/reuse-adapters.test.mjs` проверяет 18 сценариев: общий экземпляр движка,
права и проекции, чистый preview, повтор request ID, несовместимую ветку, коллизию,
неизвестные ресурсы, конкурентные резервы, устаревший остаток, освобождение резерва,
проверку fence, доступ постороннего к активному запросу и восстановление по квитанции.

Этот слой **прототипирован и проверен локально**. `MemoryStore` и
`MemoryDomainRepository` переживают создание нового экземпляра движка при сохранённых
объектах; они не переживают закрытие вкладки или перезапуск процесса. SDK также предоставляет
`IndexedDBStore` для записей операций, но эти примеры по умолчанию используют память.
Сохранять только запросы в IndexedDB и терять доменное состояние после перезагрузки нельзя:
для устойчивого примера необходимо сохранять и согласовывать оба хранилища.

Переданный `principal` проверяется как параметр локального демо. Он ещё не связан с
аутентифицированным Foundry-пользователем, socket-каналом или серверным исполнителем.
Демонстрационные закрытые тексты присутствуют в исходниках стенда; это не способ хранения
секретов рабочего мира. Для реального исполнения скрытые данные должны оставаться у
доверенного исполнителя, а участнику передаваться только разрешённая проекция.

Отдельные редакторы Studio, долговечное доменное хранилище,
настоящие журналы/базы Foundry и их автоматизации ещё не реализованы в этих примерах.
Optional SDK Core library ZIP собран отдельно из тех же исходников; его Foundry bootstrap
пока не проверен. См. SDK-LIBRARY.md.
